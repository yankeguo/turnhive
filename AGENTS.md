# AGENTS.md

turnhive is a horizontally scalable agent cluster service. It exposes only a minimal Session API (create sessions, interact over SSE, report external tool results, destroy); LLM calls, sandbox execution, skills installation and cross-node routing all happen inside the cluster.

## Build and test

```sh
go build ./...     # compile
go vet ./...       # static checks
go test ./...      # unit tests (agent / llm / storage / root-level client)
go test -race ./...  # race detector (also run in CI)
go run ./cmd/turnhive -config config.yml   # run locally (requires config.yml)
```

All of the above must pass before committing. There is no linter config file; just keep `gofmt`/`go vet` clean (CI checks that `gofmt -l` is empty).

## Project layout

```
├── client.go        # Go client SDK (package turnhive, repo root)
├── stream.go        # client SSE stream parsing
├── cmd/turnhive/    # server entrypoint (HTTP server, graceful shutdown)
├── agent/           # agent turn loop, sandbox/external tools, skills installation, history persistence
├── config/          # config file loading and validation
├── controller/      # HTTP routing and business logic (cross-node forwarding, SSE)
├── llm/             # OpenAI-compatible streaming chat completions client
├── registry/        # etcd-based node discovery, liveness and session ownership
├── storage/         # S3 wrapper (history JSONL, skill tar presign)
├── Dockerfile       # multi-stage release build (compiles in-repo, no host artifacts)
└── .github/workflows/release.yml  # CI (gofmt/vet/test/race/build) + image publishing to ghcr.io and quay.io
```

There is also a `refs/` directory holding copies of reference projects (local copies of agentdesk-runner and ironhive), deliberately left untracked by git (ignored in .gitignore); see `AGENTS.local.md` (also an untracked local document) for details. They are for reference only — there is no parity requirement.

## Code conventions

- Code, comments, commit messages, the README and this document are all written in English.
- Commit messages use lowercase Conventional Commits, e.g. `feat: ...`, `fix: ...`.
- Before adding a dependency, confirm the existing ones cannot cover the need; `llm/` is deliberately implemented with the standard library only.
- When external behavior changes (API, events, config options), update README.md and the config.example.yml comments in the same change.
- The client SDK (repo root) defines its types independently from the server; the SDK must not import server-internal packages (controller/agent etc.), to avoid leaking etcd/ironhive dependencies to consumers.

## Local development dependencies

The server requires three external services (all permanently running on this machine):

- **etcd**: `127.0.0.1:2379`, no auth.
- **S3 (RustFS)**: `127.0.0.1:9000`, no TLS, requires `force_path_style: true`; credentials are read from `~/.config/rustfs/env`.
- **ironhive**: `http://127.0.0.1:30173` (k3s NodePort); the default pool has warm standby sandboxes.

`config.yml` is the local run configuration — **it contains credentials, is git-ignored, and must never be committed**; the template is config.example.yml. Config loading is strict (unknown fields are hard errors, preventing misspellings from silently no-op'ing); the minimum `etcd.lease_ttl` is 1s (registry truncates to whole seconds for the etcd Grant).

**Gotcha**: skills are downloaded by the sandbox Pod itself via S3 presigned URLs, so `s3.endpoint` must be an address reachable from the Pod — `127.0.0.1` is unreachable inside a k3s Pod; for local verification, use the host's LAN IP instead (e.g. `192.168.1.133:9000`). `s3.endpoint` is a bare `host:port` (no scheme; whether TLS is used is decided by `use_ssl`).

## Key designs (read before making changes)

- A session allows only one running turn at a time; concurrent POST messages return 409 `session_busy`. All JSON request bodies are capped at 4MB (`http.MaxBytesReader`).
- Turns execute asynchronously: `POST messages` returns 202 + turn_id immediately, and the turn runs in a background goroutine (detached from the POST request lifecycle); events are delivered over a separate channel, `GET .../events` (SSE) — the eventHub keeps a monotonically increasing seq per session, buffers the most recent 2000 events, sends a `sync` first on connect (current turn + latest seq + the merged full message history, taken from the Loop's {user, assistant} history), supports resumption via `last_seq`/`Last-Event-ID`, and drops slow subscribers (the client self-heals by reconnecting with last_seq); every event carries `turn_id` for correlation. The turn lifecycle is the pair `turn_started` / `turn_finished`: **`turn_finished` is the single closing event of every turn** (the earlier three events `done`/`error`/`turn_cancelled` were merged), with payload `status` ∈ `done` (with `text`, the full reply) / `error` (with `message`) / `cancelled`; the hub opens/closes its currentTurn tracking based on it. `sync` is a control frame: **it occupies no event sequence number and writes no SSE `id:`** (otherwise EventSource's lastEventId would be dragged down by subsequent backlog frames, causing duplicate replays on reconnect); clients parsing a frame without an `id` fall back to the seq inside the payload.
- Turn interruption: `POST .../cancel` sets the running turn's `turnCancelCause` to `errTurnCancelled` and cancels its ctx (`CancelTurn` marks + cancels inside the lock, eliminating the "cancelled an already-finished turn" race) → `RunTurn`'s stream returns a ctx error → `failTurn` persists {user, assistant-partial}, and `hubReporter.Error` publishes `turn_finished` with status `cancelled` instead of `error` according to the cause (the `cancelTurn` of DELETE/Close sets no cause, so the status stays `error`); **the cancel endpoint waits for `finishTurn` to clear busy before returning** (the `Session.turnDone` channel), so a client resending immediately does not hit `session_busy` — recovery = resend, with no attach/auto-replay. The cancel route uses `routeSessionMode(..., allowAdopt=false)`: **a cold session has no running turn, so don't run an adoption just to cancel**. History stores only text, not tool_calls, so the working state after cancel (including unanswered tool-call pairs) is simply discarded — no dangling pairs.
- External tool results (`POST tool_results`): a result matching a waiting call_id wakes it up directly; unmatched ones are buffered in `pending` (cap 256, 429 beyond that) and cleared wholesale when the turn ends — late results neither linger in memory nor get mistakenly consumed by a later turn's same-named call_id.
- While a session is alive, its sandbox lease is renewed automatically by the controller at lease/2 intervals; all three paths — DELETE session, graceful shutdown (`Controller.Close`) and cold swap-out (`takeIfCold`) — stop renewal and release the sandbox, and DELETE/Close additionally cancel any running turn first. Any new session-lifecycle path must maintain these three cleanup paths.
- Cross-node routing relies on etcd ownership records plus the `X-Turnhive-Forwarded` header to prevent forwarding loops; an already-forwarded request is never forwarded again (and never adopted). When a node's keepalive breaks (lease lost), the registry automatically re-registers the node record with backoff (starting at 1s, capped at 30s, until success or Close); on success the `OnReconnected` callback lets the controller re-register the ownership records of in-memory sessions (`ReregisterSessions`).
- Crash recovery (hot/cold sessions, `controller/adopt.go`): at session creation the spec is persisted to `sessions/{id}/spec.json` (containing model/MCP header credentials — same trust domain as history); DELETE removes the spec (history/persisted are kept), and a failed creation rolls back by deleting the spec, preserving the invariant "201 ⇔ adoptable". When `routeSession` finds no ownership record, it adopts via `adoptSession`: load the spec + List to rebuild the persisted list (the list has no standalone object; the key is the path) → `ClaimSession` (etcd Txn put-if-absent) to claim ownership → build a history-only Loop (`buildLoop(sess, nil)` + LoadHistory + `SealInterruptedTurn` to seal the dangling user message); the first message's `ensureSandbox` then builds the full Loop with a sandbox. **Concurrency convergence**: `c.adopting` (id → chan) makes concurrent local/forwarded requests on the same node wait for the first adoption to finish — no duplicate work, no mid-adoption 404 for the loser. A session idle beyond `session.cold_timeout` (default 0 = disabled, must be > idle_timeout) is swapped out by the sweeper as a cold session (`takeIfCold` sets closed, detaches the sandbox, `hub.closeAll()` kicks subscribers, deletes the etcd key), and the next access revives it via adopt; **after adopt/swap-out the event seq restarts from 0, and clients must reset from the sync frame**. Known limitation: within a keepalive gap, another node may adopt a session that the old node still holds in memory, causing brief dual ownership; `OnReconnected` only narrows the window, it does not eliminate it.
- LLM history persists only {user, assistant} pairs (S3 JSONL); tool interaction is transient within a turn. **Write-ahead**: at turn start the user message is persisted before execution (a crash never loses user messages); a failed turn (streaming error, max steps exceeded) additionally stores the assistant-partial, with `failTurn` saving via `context.WithoutCancel` + 10s timeout, detached from the cancelled turn ctx. History persistence is always best-effort: memory is authoritative, and a save failure does not retract an already-published `turn_finished` event (the error is returned to the caller for logging); on Load, corrupt/over-long lines are skipped one by one, so a single bad line cannot lock a session.
- Context-window management (`model.max_context`, 0 = disabled, modeled on agentdesk runner's context.ts): before a turn, `TruncateToFit` drops the oldest history whole turns at a time, estimating tokens as chars/4 (budget = max_context − 8000 reply reserve − system estimate; however small the budget, the last complete turn is kept); after a turn whose usage exceeds 0.8× the window, `CompactMessages` compresses history older than the most recent 2 turns into a structured `<context-summary>` user message (a deterministic text summary, no LLM call) and writes the S3 history back.
- Sandbox paths are always relative (no WORKDIR assumption); `..` escape is rejected lexically; skills are installed under `./.agents/skills/<name>/`, and that tree is read-only to write/edit/apply_patch. Absolute paths pass straight through (sandboxes are disposable).
- The shell is stateful: ironhive reports the post-execution working directory and full environment per call via cwd/env events, and turnhive passes them back on the next foreground call (`strict_env`), so `cd`/`export` persist across calls within a session (only calls that complete in the foreground update the state).
- Shell output is redirected from the very start into the sandbox at `.agents/shell-logs/<callID>.{stdout,stderr,exit}` (the true exit code is in the .exit file; the SSE exit event is only a fallback): foreground calls read it back after completion, byte-exact; when the 30s foreground window expires or `bg: true` is set, the process is not killed but backgrounded, reporting the pid (ironhive pid event, i.e. the pgid) + output file paths, and the model uses `tail/cat` to view output and `kill -- -<pid>` to kill the whole group. Background processes die with the sandbox (on idle reap / DELETE / Close the stream breaks; the watcher discards silently and sends no notification).
- Background process exit notifications (`BgProcessExit`, aligned with the runner's bg-notifier): after a shell call is backgrounded, its goroutine is already waiting on the SSE stream for process exit (ironhive has no server-side timeout); backgrounding attaches `watchBgProcess` to consume the outcome — a clean exit calls back `OnBackgroundExit`, and a stream error (sandbox death/disconnect) is discarded silently. On the controller side an exit is first queued via `recordBackgroundExit`, then flushed by `drainBackgroundExits`: when idle it immediately starts a synthesized-user-message turn via `runTurn` (the turn-start path extracted from handleCreateMessage) in the `<background_processes_exited>` format; when busy it requeues, and the drain at the end of the turn-end defer chain flushes it — multiple exits merge into one message, each exit is reported exactly once, and the synthesized message enters history as a user message (no new event type for clients). Deliberately not doing the runner's "inject running-process status before every user message" (it pollutes the persisted history).
- Tool output is truncated in two tiers (modeled on agentdesk runner): `read` self-truncates with its own 2000-line/50KB budget (directory listings go through the same budget; the file read itself has an 8MB memory cap); all other tools (including tool error text) go through the stricter 500-line/16KB tier, and oversized full output is written by `OutputSpiller` to the sandbox at `./.agents/tool-results/<tool>-NNNN.txt`, with the model receiving only a head preview + file path + reading hint (a spill failure degrades to plain truncation). Foreground shell results read back have a 4MB memory cap; beyond it the model is told to look up the full files in `.agents/shell-logs/`.
- `load_media` is only mounted when `model.features` includes `support_image` (`ImageTool.ExecuteImage` returns a data URI); images are injected into the next request right after their tool message as a user message (image_url parts) — chat completions only accepts images in user messages; images are transient and do not enter history.
- MCP (`agent/tools_mcp.go`, official go-sdk, SSE / Streamable HTTP only, no stdio): **connected on the fly per turn** — mounted at `RunTurn` start, disconnected by `closeAll` at turn end, so it occupies no session cleanup path; tool names are namespaced as `{server}__{tool}` (server name validated as `^[a-zA-Z0-9_-]{1,32}$` and unique; a namespaced name violating the OpenAI function-name constraint or colliding with an existing tool is skipped outright); `transport` defaults to auto (streamable first, fall back to legacy SSE, **fallback only on connect failure**, not on list failure); a single server's connect/list failure is only logged via `OnMCPStatus` and never drags down other servers or the turn. **Gotcha**: the legacy SSE transport's hanging GET is bound to the connect ctx, so connections use a dedicated `sessCtx` (derived from the turn ctx, cancelled by closeAll); the 10s establishment cap is implemented by racing against a timer — never put a timeout/defer cancel directly on the connect ctx; streamable sets `DisableStandaloneSSE` (turn-scoped short connections need no server push channel). MCP tool output goes through the generic `TruncateSpill` (500 lines/16KB + spill); `IsError` results are converted into Go errors for the reply.
- The `persist` tool uploads a sandbox file to S3 `sessions/{id}/persisted/<path>` (re-persisting the same path overwrites in place) and records `PersistedObject{path, object_key, size, at}` as a **session field** (deduplicated by path), delivered with the event stream's `sync` frame — it is not a footnote of a single tool call; object_key is relative to the store prefix (same convention as SkillSpec.ObjectKey). persist is not only for final artifacts: key intermediate artifacts should also be persisted — it is the material basis of session recovery. **Both directions transfer via presigned URLs with the sandbox talking to S3 directly**: upload uses `PresignPut` + `/agent/v1/file/upload` (PUT), download/restore uses `PresignGet` + `/agent/v1/{file,tar}?url=`; turnhive never proxies bytes.
- User file input (`agent/uploads.go` + `POST /v1/sessions/{id}/files`): the reverse channel, symmetric to persist. turnhive and the caller **share the same S3 bucket, files are always passed as object_keys, and turnhive never proxies bytes** — the caller PUTs into the bucket itself, then registers `{name, object_key, size}` at any time via `POST files` (name validated as `^[a-zA-Z0-9][a-zA-Z0-9._-]{0,127}$`, deduplicated by name within the session, cap 64). Recorded as the session field `uploads` and persisted to `sessions/{id}/files.json` (best-effort, not removed by DELETE, loaded and restored on adopt), delivered as the `files` field of the `sync` frame. Injection: with a live sandbox, `InjectUploads` runs immediately (`PresignGet` + `/agent/v1/file?url=` → `./.agents/uploads/<name>`, 30s cap, failure returns 502 without registering); a cold session gets the full injection at `ensureSandbox` time (alongside RestorePersisted). **Whether/how a message references files is entirely up to the upstream**: turnhive only fixes the location `./.agents/uploads/<name>`, prescribes no marker format, and the `POST messages` content enters history verbatim. For auditing/stats, `GET /v1/sessions/{id}` returns `{id, turn_id, files, persisted}` (no SSE needed).
- Sessions are decoupled from sandboxes (unlimited recovery): the sweeper reaps the sandbox of sessions without turn activity per `session.idle_timeout` (session/hub/history are kept); the idle decision and sandbox detach happen inside a single lock critical section (`takeSandboxIfIdle`, mutually exclusive with startTurn); the next message rebuilds via `ensureSandbox` — allocate a new sandbox → reinstall skills → `RestorePersisted` to restore files → rebuild the Loop and `LoadHistory` (history lives in S3 anyway) → restart renewal; session close (DELETE / `Controller.Close` / cold swap-out) sets the `closed` flag, and `setSandbox` rejects a closed session, immediately releasing the newly built sandbox and its renewal goroutine (preventing orphan leaks). **All sandbox file injection goes through S3 presigned URLs with the sandbox pulling by itself** (skill tars via `/agent/v1/tar?url=`, persisted files via `/agent/v1/file?url=`); turnhive never proxies bytes. When changing the session lifecycle, this rebuild chain and the three cleanup paths (DELETE / `Controller.Close` / cold swap-out) must be maintained.
- Egress calls uniformly carry the fixed header `X-Turnhive-Session: <session-id>` (`agent.SessionHeader`, injected in `agent/loop.go`: every LLM step request and every MCP connection is injected via `withSessionHeader`, and **any same-named header in the spec is dropped case-insensitively**, preventing impersonation of another session). Upstream may use it to derive user/permissions for gating and attribution (trusted internal network), or ignore it and let turnhive talk to providers/MCP directly; gating decisions belong entirely to the upstream deployment — turnhive makes no callbacks.
